# Аудит CloudMind — 8 октября 2026

Проверены две копии Node/TypeScript backend, маршруты и SQL основных функций, Flutter API/авторизация/чат/дневник/подписки, тесты экранов, хранение сессии и обмен с native-виджетами. Выполнены статический анализ, сборки TypeScript, автоматические тесты и npm-аудит. Это аудит кода и локальные проверки; он не означает, что все сценарии прошли на настоящем сервере или что уязвимостей больше нет.

## Запросы БД: что изменилось

- Список чатов больше не объединяет и сортирует всю историю всех пользователей. `LEFT JOIN LATERAL` берёт по последнему сообщению из `user_chat`/`ai_response` для чатов владельца. Нужны уже описанные в `migrations/add_indexes.sql` индексы `(chat_id, senddate DESC)`. Ускорение не измерено без БД.
- Поиск дневника использует диапазон `diary_date >= day AND diary_date < day + 1 day`, позволяющий использовать `(user_id, diary_date)` вместо функции над индексируемым столбцом.
- Убран дополнительный запрос статистики лимитов, выполнявшийся после каждого ответа чата только ради лога.
- Статус сессии запрашивается один раз на HTTP-запрос. Индекс PK session.id достаточен для этой проверки; добавлять дублирующий индекс по id не нужно.
- Квота списывается одним условным UPSERT, который не пропустит два конкурентных запроса сверх лимита. Получение тарифа остаётся отдельным SELECT.
- Подготовлен `backend/migrations/audit_performance_indexes.sql` и копия во Flutter-backend: дневник, lower(email), задания, владелец аудиофайла. Индексы создаются CONCURRENTLY, вне транзакции; перед применением нужно проверить уже существующие эквивалентные индексы. Файл не применён.
- Логируются медленные SQL-запросы >500 ms; в DB helper не выводятся параметры/полный объект ошибки.

Для следующего измеримого этапа на подключённой БД: снять `EXPLAIN (ANALYZE, BUFFERS)` только SELECT списка чатов, истории, дневника и inbox для обычного и большого аккаунта; измерить p50/p95, количество запросов на экран, pool.waitingCount. Сопоставить seq scans с размерами таблиц, проверить pg_stat_statements, статистику autovacuum и дубли индексов. `ANALYZE`-план выполняет запрос: для изменяющих команд его не запускать на пользовательских данных.

## Что остаётся и мешает считать систему готовой к production

1. **Нужен интеграционный прогон на тестовой PostgreSQL/Redis.** Сейчас настоящая БД недоступна. Сборка TypeScript не доказывает наличие таблиц/колонок. В проекте сосуществуют `messages`, `user_chat`, `ai_response`, `chat_id`, а также разные модели подписок. Голосовые сообщения и обычные сообщения сохраняются разными путями, поэтому превью/история могут расходиться. Требуются единая схема, миграционный baseline и сверка реальных API с Flutter.
2. **Две копии backend остаются архитектурным риском.** Важные исправления продублированы, auth/OAuth выровнены, но остальные файлы не полностью одинаковы. Выбрать один запускаемый backend, второй заменить ссылкой/общим пакетом или удалить после проверки deployment. Старый web-проект `silencexx` не запускался в этом аудите: актуальным клиентом принят Flutter.
3. **Регистрация по email ещё не транзакционная.** Сбой между созданием description/role/session/user/settings оставляет частичные записи; предварительная проверка email не защищает от двух одновременных регистраций. Нужны транзакция, единая нормализация, проверка дублей и UNIQUE INDEX LOWER(email). Нельзя создавать уникальный индекс на живой БД без проверки существующих дублей. Подтверждение email при регистрации также не реализовано.
4. **Журнал и создание daily task имеют гонку check-then-insert.** Транзакционная защита завершения задания сделана, но уникальность одной записи дневника/одного задания за день нужно обеспечить на уровне схемы и атомарной вставки. Предварительная проверка перед AI недостаточна. Продуктовая логика дневника сейчас отвергает кризисный текст вместо сохранения с предложением поддержки — требует пересмотра.
5. **Inbox: ограничения 8/3 часа проверяются отдельно от записи.** Параллельные запросы могут выбрать одного получателя или отправить несколько пожеланий. Требуется транзакционный claim отправителя/получателя (`FOR UPDATE SKIP LOCKED` или условный UPDATE) и откат при ошибке. `ORDER BY RANDOM()` сортирует множество пользователей; заменить на измеренный способ выборки из доступных получателей/очередь.
6. **Квоты теперь учитывают попытки до генерации.** Это защищает от конкурентного перерасхода, но не делает возврат квоты при ошибке валидации/AI. Нужна явная политика refund/idempotency и отдельное состояние reservation. Повторный запрос после сетевого таймаута всё ещё может создать второй оплаченный вызов: автоматический retry Qwen отключён, но клиентский retry требует idempotency key. Panic и отклонённые модерацией пожелания ограничены общим rate limit, не отдельным денежным бюджетом пользователя.
7. **Оплата, привязка OAuth и SMS требуют настоящих интеграций.** Нельзя вернуть демо-подтверждение в production. Для подписок нужны проверка транзакции на сервере, idempotent webhook, возвраты и отмена автопродления без досрочного отнятия уже оплаченного периода. OAuth пока требует email в подписанном токене; стабильная таблица `(provider, subject)` и аутентифицированная привязка аккаунтов нужны отдельно. JWKS-кэш обновляется раз в 5 минут; для ротации ключей стоит добавить контролируемое обновление при новом kid.
8. **Голосовой pipeline требует нагрузочного теста.** Процесс Python запускается на запрос, язык захардкожен `ru`, нет надёжной очереди с восстановлением после рестарта. Нужны ограничение параллелизма, таймауты, очистка временных файлов, согласование статусов между chat/API/Whisper. `exec` желательно заменить `execFile` с массивом аргументов; прямую клиентскую shell-инъекцию по просмотренному пути не подтвердил, поскольку пути формирует сервер.
9. **Жизненный цикл файлов/данных.** Нет полноценной политики удаления voice/avatar файлов после ошибки/смены аватара/удаления аккаунта. Нужна очистка диска и retention AI ledger, журналов, pending reset/email tokens. Токены восстановления хранятся в БД открытым значением; предпочтительно хранить хеш. Часть обработчиков ещё логирует полные исключения.
10. **Масштабирование rate limit.** Текущее хранилище счётчиков IP находится в памяти процесса; для нескольких экземпляров нужен общий Redis-store. `TRUST_PROXY_HOPS` задавать только по фактической цепочке прокси с закрытым прямым доступом к серверу; иначе возможны общий IP всех клиентов или подмена адреса.
11. **Android-виджет хранит JWT в private SharedPreferences.** Backup отключён, но для защиты токена на диске лучше Android Keystore. iOS использует Keychain. Требуются native-тесты смены аккаунта, отзыва сессии, смены языка/часового пояса, обновления после полуночи и восстановления после перезагрузки. Видимость виджета при системной блокировке приложения Face ID — поведение iOS, ранее подтверждённое пользователем.
12. **Остались 2 moderate npm-записи:** Bull и его транзитивный uuid относятся к [одной проблеме bounds check в uuid v3/v5/v6](https://github.com/advisories/GHSA-w5hq-g745-h8pq). Просмотренный Bull использует v4; это снижает применимость этого пути, но не является доказательством безопасности всей зависимости. Предложенный npm `--force` откатывает Bull на 1.1.3: такой несовместимый откат не применялся. Нужна проверенная миграция очереди/обновление зависимости.
13. **Клиентские ограничения и локализация.** Файл в чате допускает 24 000 символов, а AI принимает сообщение до 8 000; согласовать UI и backend. Выбор изображений не превращает текстовый qwen-flash в vision-модель. Часть ответов panic/Whisper остаётся английской/русской независимо от языка приложения. Резервный panic-текст утверждает безопасность тела без данных — такие утверждения нужно убрать при отдельной проверке сценариев поддержки. Контакты помощи должны соответствовать выбранной стране, а не автоматически России.
14. **Адрес сервера по умолчанию — временный ngrok-домен.** Для релиза нужны стабильный HTTPS endpoint, отдельные dev/staging/prod конфигурации, проверка CORS для web и мониторинг. Доступность этого endpoint не доказывается успешными mock-тестами.

## Перед следующим запуском

Локальный `backend/.env` получил новый случайный JWT_SECRET. После перезапуска пользователям понадобится повторный вход; текущий запущенный процесс не перезапускался. В deployment следует задать собственный сильный секрет. JWT/ключи не добавлены в Git.

Qwen-ключ пока отсутствует. Для Aiven/частного CA может потребоваться `DB_SSL_CA_FILE`, поскольку небезопасное отключение TLS-проверки устранено. Оплату и телефонный вход нельзя считать рабочими: они намеренно закрыты до реальной проверки провайдеров.

При подключении тестовой БД приоритет: migrations/schema → регистрация/вход/выход/сброс → чужие chatId/jobId/audio → параллельные квоты → текст/голос/дневник → inbox/streak → native widgets → нагрузочные планы SELECT. После этого можно оценивать реальную задержку, стоимость AI и готовность к выпуску.
